si-didy-loop

Every night a small AI model on one ordinary laptop dreams up a small piece of software, writes it, tests it and keeps notes on what it learned. si-didy-loop is the set of tested rules that keep that night honest: what the model is reminded of before it dreams, which of its notes may leave the machine, what it may post, which actions wait for a person's signature, and the single page that person reads in the morning.

Each rule is a small, pure piece of code (a kernel: no clock, no files, no network) with its own tests, and every kernel is mutation-tested on GitHub's runner on every push: the gate changes the code on purpose and the tests must notice. The numbers on this page are read from the repo's own receipts, which CI re-derives, so none of them is typed in.

How it works

The night is a loop. Before it dreams, the resident (the local model, Qwen 2.5 7B through Ollama on this laptop) is handed its own most-repeated dream titles from recent nights. It writes a title and an idea, then code and a test for it. The code is run against its own test and then mutation-tested; failing code gets revision rounds. The resident writes a note, and if it wants the note to leave the machine, the share door judges it. Every step is stamped into a private ledger on the machine, and the next night's reminder is folded from that ledger.

Counts beside the boxes are the sealed week (window B) from dream-week.json and night-trace.json.

Around the night

The same repo holds the parts of the loop that act during the day, each gated the same way: the operator runs operational work on its own (building, gating, drafting) but queues a payment, a spend, a binding commitment, anything legal and any venture going live until the key-holder signs it (Ed25519; the operator holds only the key-holder's public key, so it can check the key-holder's signature but never make it; its own key pair signs only its own work, and approval refuses any signature but the key-holder's); the rail is the one outward action that runs without a signature, and its runner sends a post only through postScrubbedProven: the model's fingerprints scrubbed first (scrub.mjs), then every claim checked against the build receipt the draft carries (receiptgate.mjs: no receipt, no post), then its score, spacing and daily cap; and the morning brief folds the night's files into one page ending in one first action, and is never published.

What the fold fix changed in the prompt

The week also showed why the reminder list was weak: the 7B re-dreams one thing under version markers (++, +++, Optimized, Redux…). The fold already ignored punctuation, but the words split the family and the prompt named the latest spelling. The fold in this repo now strips trailing version markers (…, and V followed by digits) before counting, gated by its suite and witness. Its first version was one regular expression whose time grew exponentially with a gap of spaces or plus signs inside a title, so one strange title could have hung the night's fold; it now reads the same rule right to left, one marker at a time, in time linear in the title, and its suite holds it to the first version's answer on 20,000 generated titles and times a 100,000-character gap. The resident's night carries its own byte-for-byte copy of this file on the laptop; until that copy is replaced with this one, the night still folds by exact spelling. Adoption

What it does for a team: if you run any AI work unattended (an overnight agent, a batch that writes code or copy, a bot that posts), you wake up to output nobody watched being made. These kernels make that output checkable in the morning: every step is timed in a ledger you hold; code the model writes is run against its own test and mutation-checked before it is trusted; a note leaves only with a reason that names something checkable; a post goes out only if a build receipt backs every claim in it; a payment, a spend, a binding commitment, anything legal or a launch waits for a person's signature; and a weekly question is written down before it is measured, with failures kept.

What it needs: Node.js 20 or later and git; the kernels have no dependencies. For the night itself, a local model server (Ollama) with a model that fits the machine's memory: on this laptop the 14B did not fit and timed out, and the 7B does. The model and Ollama are separate software under their own licences. The runners also expect the sibling checkouts they load beside this one (missig, generative-estate, fallkard-forge, fallforce), and they carry one machine's paths until you point them at yours.

How a team rolls it out

  1. Gate it on your own CI first. Fork, keep .github/workflows/ci.yml, and let your runner reproduce every verdict in receipts/gates.json. Nothing else is trusted until that is green.
  2. Run the doors read-only over logs you already have. Feed last month's agent notes through judgeShare and last month's job titles through foldDreams. That is how the share door was proven before it went live: a backtest over the real shares log.
  3. Wire the runner to your paths. The kernels never touch files; the runners in scripts/ do, and they are written for one machine's paths. Point them at yours, and keep state in safejson files so a crash mid-write cannot kill the next night.
  4. Make the key yours. Generate the operator's key pair on the key-holder's machine (scripts/master-key.mjs --init); the night only ever holds the public key, so it can prepare a threshold action but never execute one.
  5. Switch on outward actions last. The rail needs a platform token pasted by the key-holder into a local config file; it never rides through chat, a repo or a prompt, and the brief never prints it. Once the token is in, posts need no signature, so the draft writer must attach the build receipt each post's claims rest on: a draft without one is refused at the gate and stays in the outbox.
  6. Seal a week check before you look. Write the claim, the windows and the definitions in a new file, commit it, then measure with a kernel, and keep the result whichever way it falls.

Benefits by role

CEO

One page each morning ending in one first action, instead of a heap of logs. Anything the system says in public is limited to what a build receipt backs, so an AI cannot overclaim in the company's name.

CFO

The work runs on a model on hardware you already own, so the running cost is electricity, worked out below from sourced figures. The code is MIT-licensed: no seat licence and no subscription for the kernels.

COO

The night runs on its own as scheduled tasks, and its state survives a crash mid-write. A runner fault is recorded as the runner's fault ("no render"), not learned by the model as a lesson, so the process does not quietly teach itself the wrong thing.

CTO / CISO

Pure kernels (no clock, no files, no network), mutation-gated on GitHub's runner. Threshold actions need an Ed25519 signature the system cannot make. The posting token lives only in a local file the brief is tested never to print. The ledger stays on the machine.

Engineering

Code the model writes arrives with its own test and a mutation verdict, so a reviewer starts from what was proven, not from a guess. The week check is a template for measuring an AI change honestly.

Comms and operations

No platitude leaves the machine: the share door shuts reasons that name nothing. Posts go out on the platform's own sanctioned rail, spaced and capped, scrubbed of model fingerprints, and only with claims a receipt backs.

    Security and data protection

    • Your data stays on your machine. The ledger, the notes, the knowledge graph and the morning brief are local files; the graph and the brief are kept out of the repo by design because they carry private names.
    • The kernels cannot leak. They make no network call and read no file; data goes in as an argument and a verdict comes back.
    • This repo's code reaches two places, and you choose both. The wisp's runner talks to the local model at localhost:11434 (Ollama, on the same machine) and refuses any other address; the rail's runner talks to graph.facebook.com, only once the key-holder configures a token, and refuses any other origin at the wire (the rail kernel can also shape a LinkedIn request; the runner does not send one). The nightly runner also loads or starts code kept in other folders on the machine: the forge studio (fallkard-forge) the operator builds with, the fallforce kernels the course drills on, the soul's session digest and the estate ladder's evidence scan. Those are separate code with their own reach; check them before you run the night.
    • Nothing with money or legal weight runs unsigned. Payments, spends, binding commitments, legal acts and launches are classified by a frozen table the system cannot change; an action the table does not know is treated as one of them. The only outward action that runs on its own is a post on the sanctioned rail, and only through the receipt gate.
    • Nothing reaches the supplier. There is no telemetry and no call home in this code; the supplier sees nothing unless you send it.
    • Model-written code is run, so choose where. The resident's sandbox runner (on the machine, outside this repo) runs each dreamed kernel's own test with Node in its own folder under a time limit, then the mutation gate. That is a time limit and a folder, not an operating-system sandbox, so run the night under an account that holds nothing you would not let a test script read. The wisp's path in this repo (wispwire.mjs) goes further: it refuses model code that imports, requires, fetches, touches the process, evaluates strings, sets timers, reads the clock or draws random numbers before its field may run it.
    • A post is public, and the rail does not look for personal data. It scrubs the model's fingerprints and checks every claim against a receipt; it does not search a draft for names or personal details. A post carries whatever its draft says, so keep the drafts about your builds, and the token stays out until you choose to paste it.
    • Secrets never enter a prompt. The posting token is pasted by hand into a local config; the brief's suite asserts no printable brief contains it.
    • Every gate is reproducible. Anyone can re-run the mutation gate at the pinned witness version and get the same verdicts the receipt shows. The pin is the tag v0.6, and CI fails if that tag ever stops naming commit f04fe30, so nobody can move the gate under the receipt.

    Risks, answered straight

    • It was built for one estate. The kernels are general; the runner scripts carry one machine's paths and need wiring to yours (step 3).
    • The share door is a floor, not a grade. It stops reasons that point at nothing; a model can learn to name an estate word in a thin reason.
    • Small local models write weak code. In the measured week … dreams produced code that passed its own gate. The gate is what stops the rest being trusted; it does not make the model better.
    • One of the two week predictions failed. Naming the repeats did not make them fall (W2). The model changed the same day, so the two effects cannot be separated from this week alone. Both are kept on the record.
    • Posting depends on the platform. If a platform refuses the token's permissions, the rail refuses to post and the morning brief says so; it never works around the platform.
    • The night needs the machine awake. A laptop that sleeps holds its scheduled tasks until it wakes, so the night runs late or is cut short by its own time limits. Run it on a machine set to stay awake overnight.
    • A draft with no receipt never goes. The receipt gate is strict by design: a post that cites a link, a score, "live" or "CI green" needs a build receipt that backs each one. A team whose drafts carry no receipts will see the rail refuse every one, loudly, until they do.

    The case for the board

    Unattended AI is cheap to start and expensive to trust. This is a way to run it where the trust is earned in public: every rule is code with a test, every test is attacked by a mutation gate on a neutral runner, every claim the system makes outward is limited to what a receipt backs, nothing with money or legal weight moves without a person's signature, and the company measures its own AI changes by writing the prediction down first and keeping the failures. It runs on hardware the company owns, under a licence the company keeps.

    White paper: keeping an unattended AI honest

    The problem. A model that works while nobody watches produces output that looks like progress. In this estate's own night, looking closely found five kinds of theatre: nightly "ideas" that were one fill-in template over three names; a memory probe that scored zero by construction because the model was never shown the memory it was asked about; a share rule ("an explicit reason, logged and justified") that had quietly narrowed to "three real words", so platitudes went out; a reminder list folded from a log that had stopped moving, so it named the same dead lessons every night; and a model too big for the laptop, whose timeouts the resident then wrote up as lessons.

    The method. Each fix is a small pure kernel with its own tests, mutation-gated on a neutral runner, and wired by a separate runner script. Words come from evidence only (plainsay says a route from the edges it walked, or says that a reason was not kept). Doors are floors with written refusals (sharedoor, operator, receiptgate). State survives crashes (safejson). Runner faults are named as runner faults. And a change to the night is judged by a claim sealed before the measuring code exists.

    The result so far. Moving the night to a model that fits raised the share of dreams that became code (W1 holds). Naming the resident's repeats did not reduce them in that week (W2 fails); the fold that names them now counts a title's whole family, so once the resident carries it the next measurement is about the real repeat rather than its latest spelling. Only a small share of the code passes its own gate, which is the gate doing its job.

    The limits. One laptop, one resident, one week, two changes on the same day. The check is recorded, not blind. The doors are floors, not judges of quality. None of this makes the model wiser; it makes what the model did checkable.
